## 1. Decisions

**D1 - Last slot.** The quick grid becomes 5 emoji (`❤️ 😂 👍 🎁 😮`) + a 6th tile `.reaction-sheet-btn.reaction-sheet-more` showing a text `+`, `aria-label="Więcej emoji"`. Still a 3x2 grid, same 56px tiles. 🙏 stays in `CHAT_REACTIONS` (name `podziękowanie`, order index 5, still renders/labels/sorts exactly as before) but is no longer a quick tile; it is reachable in the full picker (People & Body). No "recently used" row (explicitly not over-building). Fail-soft: if `window.EmojiData` / `window.EmojiPicker` did not load (stale cache), the 6th tile falls back to 🙏 so the sheet never loses a working control.

**D2 - Picker engine: self-contained, bundled static dataset, no library.**
- New `public/emoji-data.js` (generated, committed): a dual-module IIFE (same shape as `pluralize-pl.js` / `chat-reactions.js`) exposing `EmojiData = { version, categories: [{ id, label, icon, emoji }] }` where `emoji` is ONE space-separated string of fully-qualified emoji per category (strings, not objects, to keep it small).
- Generated by a one-off dev script `scripts/build-emoji-data.js` from the pinned Unicode file `https://unicode.org/Public/emoji/15.0/emoji-test.txt` (Emoji 15.0, Sept 2022). Rules: keep `fully-qualified` lines only; drop the `Component` group; drop any sequence containing U+1F3FB..U+1F3FF (skin tones are out of scope); assert max code points per emoji <= 16 (DB column) and fail otherwise; group order as in the Unicode file. The script is dev-time only (no runtime or package.json dependency; uses Node's global `fetch` or a local file path argument). The generated file records the source URL and Emoji version in a header comment.
- Expected size: roughly 1,400 emoji, ~12-16 KB raw, ~6-8 KB gzipped (server uses `compression`). The coder must print the real number in FEAT-001's `findings`.
- New `public/emoji-picker.js` (~200 lines, no knowledge of reactions): `EmojiPicker.create(container, { onSelect(emoji), isSelected(emoji) })` -> `{ show(), refreshSelected(), focusFirst(), reset() }`. Renders a tab row (one tab per category) and a scrollable grid of the ACTIVE category only (<= ~330 buttons, so no 1,400-node DOM).
- Rejected: `emoji-mart` (hundreds of KB, ships its own data), `emoji-picker-element` (fetches a CDN dataset into IndexedDB - breaks the offline/CDN-blocked requirement), `unicode-emoji-json` (would be a new npm runtime dependency just to read a file we can generate once).
- Search: SKIPPED in v1. The UI is Polish and the only free data is English CLDR names (~+35 KB); a half-useful English search is worse than none. Category tabs + scroll cover "all emoji". Per-emoji accessible names are NOT bundled either: the grid buttons contain the glyph as text (not `aria-hidden`), so the platform screen reader announces the emoji in the user's own language.
- Known limit (document in the final summary): an OS whose emoji font predates Emoji 15.0 draws newer glyphs as boxes. No runtime font-support probing (over-building).

**D3 - One sheet, two views (not a second dialog).** The existing `#reactionSheet` gets a mode. Quick mode = today's grid. Full mode (`#reactionSheet.is-all`): header shows a back button (`#reactionSheetBack`, "Wróć do szybkich reakcji", text glyph `←`) + title "Wszystkie emoji" + the existing close button; body shows `#emojiPickerRoot` (tabs + grid) and hides `#reactionSheetGrid`. Reusing the dialog keeps the overlay, outside-tap close, Escape, `inert`/`aria-hidden` handling, z-index (10001 > tab bar 9999 and toasts 9999) and the focus-return logic exactly as they are. Escape and overlay tap close the WHOLE sheet in either mode; the back button is the only way back to quick mode.
Gotcha: `.reaction-sheet-grid { display: grid }` beats the UA `[hidden]` rule - add `.reaction-sheet-grid[hidden], #emojiPickerRoot[hidden] { display: none; }` or the quick grid stays visible under the picker.

**D4 - Picking uses the SAME code path as a quick reaction.** The picker's `onSelect(emoji)` calls the existing `toggle(sheetMessageId, emoji)` (`chat-reactions.js:~400`) and then `closeSheet()` - identical to the current grid click handler (`:~512-519`). So: optimistic update, same `POST /api/wiadomosci/messages/:id/reactions`, toggle-off when already reacted (the picker marks emoji with `mine` as `aria-pressed="true"`), the per-key `inFlight` debounce, rollback + toast on error, and the server throttle `REACTION_RATE_MAX = 30 / 10s` (`lib/chat.js:84-85`) all apply unchanged. No per-message distinct-emoji cap is added (that would be new reaction semantics; the chat has two participants, chips wrap, the throttle exists) - mention it as a known, accepted risk.

**D5 - Server validation = exact membership, not a regex.** `isAllowedReactionEmoji(e)` becomes: `typeof e === 'string' && e.length <= 32 && ALLOWED.has(e)` where `ALLOWED = new Set(CHAT_REACTION_EMOJI ∪ every emoji in EmojiData)`. Rationale: a "single grapheme cluster" regex needs `\p{Extended_Pictographic}`, keycap, flag and tag-sequence special cases and still lets through non-RGI junk; membership in the same dataset the UI offers is exact, tiny, testable, rules out HTML/control characters and multi-emoji strings by construction, and cannot drift from what the picker can send. `chat-reactions.js` loads the data via `require('./emoji-data')` in Node and `root.EmojiData` in the browser. If the data is missing it fails CLOSED to the legacy 6 (never open). The client always sends fully-qualified sequences (what the dataset contains); an unqualified `❤` is rejected with the normal 400 - acceptable.

**D6 - Order.** Total order for chips: the 6 legacy emoji keep indices 0-5 (so existing chips/tests are unchanged), every other emoji sorts after them in dataset order (`100 + index`). One `orderOf(emoji)` function replaces the three `EMOJI_ORDER.get` uses.
